# 候选研究方向：问题成立、最近工作、实验和停止条件

> **2026-10-29重要更正：方向一的原A类主线推荐撤回。** [Retire](https://arxiv.org/abs/2610.01160)已直接覆盖版本化切换、停止过期计算、有效状态继承与连续修订；仅迁移到手机不足以主张新问题。下文保留历史假设和实验细节，不作为当前优先级。最新候选及最近先例见[新版汇报稿](08_mobile_agent_inference_research_briefing_20261029.md)。

截止2026-10-27。以下是**研究假设和筛选方案**，不是已验证结果，也不是“首次”声明。建议同时做两个很小的问题测量，选一个主线；不要把四个方向合并成大系统。

## 1. 方向一：依据会失效的推理请求，应该何时取消、何时继续

**优先级：A，优先做问题测量。** 和你现有的多Session请求事件、QNN分段调用最容易形成联系，也能将贡献从KV策略移向任务语义与计算生命周期。

### 1.1 问题是否存在

手机Agent根据屏幕、工具结果或用户请求开始推理；其间可能出现页面切换、通知、外部数据更新或用户改口。推理完成并不保证结果仍可执行。如果服务层只知道一段prompt，即使上层已发现失效，仍可能排队、预填充、生成，甚至阻塞新的有效请求。

Android动作重绑定论文证明观察到动作的间隙可以被利用；动态GUI、AOI和预编译策略树也已研究变化与响应时机。这能支持“值得测量”，**不能证明自然手机任务中大量推理都会过期**。[Android Action Rebinding，A13](https://arxiv.org/abs/2601.12349)、[DynamicGUIBench，B11](https://arxiv.org/abs/2604.25380)、[AOI，C20](https://arxiv.org/abs/2606.29472)、[Correct but Late，C19](https://arxiv.org/abs/2607.28399)。

先把问题限为两个可观察场景：

- **用户更新意图**：修改目标、取消任务、补充关键参数；请求版本可以由Agent Service可靠生成。
- **环境改变必要前提**：前台App／窗口改变、目标控件消失，或工具资源的版本改变；只监测与当前操作有关的前提。

暂时不把“任意截图差异”作为失效，也不声称能自动准确推断任意动作的全部语义依赖。动态时钟和视频帧变化会使全屏hash持续误报。

### 1.2 真正想研究的切片

**不是发现“屏幕会变”，而是将可观察的失效传播到服务队列和可中断执行边界，联合权衡取消浪费、保留有效工作和重启饥饿。**

一种最小契约是：`task_id, intent_epoch, observation_version, dependency_tags, useful_until?, cancel_group`。其中`useful_until`仅在App或任务确有时限时提供；不要人为给普通查联系人任务制造毫秒deadline。推理层返回实际执行阶段、可取消粒度和已完成工作量；上层在动作提交前再检查必要前提。

可以比较几种策略：排队中去掉旧版本；生成阶段在可取消边界停止；变化时合并为最新请求；对频繁但非关键变化做轻量门控。复用只允许**相同模型／模板／状态版本下仍匹配的有效前缀**。不能把旧KV任意拼接到新屏幕提示并声称等价。

关键技术问题是：

1. 哪些事件值得穿过层次边界，监测误报与漏报成本多大？
2. QNN图只能在某些边界取消时，继续当前短段还是尽快重启更好？
3. 持续变化时如何避免旧请求反复占资源，也避免最新请求永远无法完成？需要稳定区间或可执行有效动作的条件，不能无条件保证进展。

### 1.3 最近工作与必须超过的基线

| 最近工作 | 已经解决的部分 | 候选方向必须补出的差异 |
|---|---|---|
| [InterruptBench（2026-10-28补查）](https://arxiv.org/abs/2604.00892) | Web长任务执行中追加、修改和撤回要求，按动作进度注入更新并评估适应 | 用户中断与目标变化本身不新；需进一步验证手机推理运行中取消／合并旧计算的成本与价值 |
| [TOCTOU，A12](https://arxiv.org/abs/2604.18860)、[Action Rebinding，A13](https://arxiv.org/abs/2601.12349) | 动作前提可能被改变及执行前防护 | 重点是无效计算的排队／取消成本和有效任务完成；不能以安全检查本身主张创新 |
| [Commit-Time Authorization，A18](https://arxiv.org/abs/2607.10487) | epoch、依赖证据、取消分支和提交时有效性检查 | 版本契约和提交检查本身已有；候选差异限于手机执行层何时取消、合并与让出 |
| [Forgetting Without Restarting，A19](https://arxiv.org/abs/2609.04875) | 通过溯源与净化重放处理失效信息对prompt、记忆及KV的影响 | 保留前缀／重放本身不新；不能把隐私遗忘与环境变化混为同一任务 |
| [AOI，C20](https://arxiv.org/abs/2606.29472)、[LivingScreen，B12](https://github.com/BITHLP/LivingScreen) | 连续观察和观察成本 | 必须比较自适应观察，不能只打败固定周期截图 |
| [Correct but Late，C19](https://arxiv.org/abs/2607.28399) | 预先编译可枚举动作，缩短响应路径 | 主测未提前知道值、不能完整预枚举的任务；可枚举任务也需对照其方法 |
| [PastForward，C11](https://arxiv.org/abs/2609.32166) | 下一屏早推理和预测后验证 | 研究错误预测／自然更新下的取消与保留，并把早推理作为可组合或竞争基线 |
| [Agent.xpu，C07](https://arxiv.org/abs/2506.24045)、[Sereno，I15](https://www.usenix.org/conference/osdi26/presentation/xin) | 优先级、抢占、前台保护 | 证明收益来自“请求已失效”的信息，而非普通高优先级抢占 |

最低基线：普通FIFO＋完整动作前检查；执行前重观察；最新请求覆盖队列；收到取消就停止；普通优先级；固定／自适应观察；提交边界epoch检查。各基线使用相同模型、工具和监测器。不能只对比完全没有取消能力的实现。另有[上下文有效期调度预印本，C23](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=7621058)值得正式立题前补查；本轮全文访问受限，尚不能据此确认精确覆盖关系。

### 1.4 Benchmark和判别实验

主环境可从AndroidWorld任务加**可复现、可标注的扰动扩展**开始，结合AndroidReality工具；用户意图变化可先用HammerBench语义构造版本更新场景，再运行真实闭环。所有扩展应单独命名和报告，不能使用原benchmark名称冒充原始分数。[B01](https://github.com/google-research/android_world)、[B14](https://github.com/Xiao0o0o/AndroidReality)、[B06](https://github.com/MadeAgents/HammerBench)。

AOI的DynaCU-Bench与LivingScreen适合验证动态观察机制，但它们是浏览器环境；最多作为第二域，不能替代Android真机。原AndroidWorld没有天然提供意图变化和持续时钟协议，不能直接拿原分数证明该问题。

先选至少两类真实变化和一组无变化对照，分别测自然发生与受控注入。记录：有效动作／任务成功率、从最新有效目标出现到完成的时延、过期请求执行时间和能量、取消生效延迟、误取消、反复重启次数、监测开销。安全检查仍可能留下观察与注入之间的残余间隙，不应宣称截图检查实现原子动作。

**停止条件**：自然变化中几乎没有实质失效；或者动作前刷新＋最新队列覆盖就接近收益上界；或者推理段无法有效取消且大部分成本早已发生。任何一种出现，都应停止把它当主论文，或缩成测量结果。

## 2. 方向二：LLM等待工具时，手机为什么未必有空闲资源

**优先级：A，但前提是工具确实在手机执行。** 如果继续用PC执行AppWorld API，此方向目前不具备问题证据。

### 2.1 问题定义与证据强弱

不少Agent工具是OCR、图片处理、语音识别、本地检索或索引操作。它们可能与NPU推理共享CPU调度、LPDDR、GPU及中间张量内存。此时将“LLM暂停”等同于“可无代价开始别的推理”，可能导致排队、帧卡顿、内存峰值甚至进程回收。

服务器上的MARS已联合安排GPU推理和CPU工具，资源动态测量也明确发现工具差异；手机Sereno则已证明NPU与前台App存在非对称带宽争用。因此这个方向**不是首次联合调度工具与模型**。尚待验证的是：真实手机Agent的工具阶段是否造成一种现有策略不能处理的资源冲突，且需要Agent与推理服务交换信息。[MARS，C14](https://arxiv.org/abs/2604.26963)、[资源动态，C17](https://arxiv.org/abs/2609.19947)、[Sereno，I15](https://www.usenix.org/conference/osdi26/presentation/xin)。

### 2.2 建议缩成一个可证伪的问题

可以优先检查：**任务恢复时的内存突发是否被单独管理KV的服务遗漏？** 例如工具结果尚在内存、图像张量未释放，下一轮prefill已经开始；或者模型在工具处理期间不必要地维持高性能状态。这里只是待测例子，不能预先假定必然存在。

将任务表示为在线阶段序列，而不是已知完整DAG：

`observe → prefill/decode → tool → result materialization → resume`。

工具层只暴露可得到的信息：粗略资源类别、预计峰值的置信范围、是否可重试／暂停、结果大小、完成事件；服务层暴露可用内存、当前执行阶段、可让出的边界与恢复成本。不要给在线策略偷看未来轨迹或真实峰值。

第一版只控制**准入、并发上限、token批段、阶段错开和结果释放时机**。若这些公开接口已足够，不需要先改NPU内核。只有实测发现静态图粒度是主要限制，才扩展到底层。不能假定普通Android应用有任意DVFS、内存带宽配额或跨进程优先级权限。

### 2.3 最近工作和创新风险

- MARS已经有联合信息流、工具资源准入、续跑优先级与KV策略。必须实现一个适应手机接口的MARS式基线；若主方法只是改权重或换设备，不建议立题。
- Sereno已经研究共享带宽和前台平滑度。若测到的现象只是同一种NPU带宽争用，优先复用／比较它，而不是重新命名问题。
- Tandem已经研究模型常驻时释放NPU power votes。单独“工具等待时降低空闲功耗”已不足以立题。[C12](https://arxiv.org/abs/2610.26660)。
- Agent.xpu与EdgeAgent已有异构流协调和等待时让出；手机工具产生的**实际资源峰值、完成反馈和内存存活区间**必须成为有证据的区别。[C07](https://arxiv.org/abs/2506.24045)、[C09](https://arxiv.org/abs/2610.03394)。

### 2.4 可用评测和缺少的那一层

AppWorld、ToolSandbox提供任务语义和状态评估，但没有代表手机OCR／音频／索引的真实负载。需要一个很小的**真机工具执行层**，选取本来就需要这些工具的任务，保留可验证终态。不能为了制造资源争用，往原Spotify任务中凭空加入OCR。[B03](https://github.com/StonyBrookNLP/appworld)、[B04](https://github.com/apple-aiml-research/ToolSandbox)。

可采用图片内容检索／提取到结构化记录、音频转写后检索或摘要等有清楚输入输出的任务，配合固定版本的本地工具。初期可以人工检查任务合理性和写确定性checker；是否能迁移某个原benchmark的任务必须逐项核实。Android AppFunctions可作为函数接口参考，但处于预览且不能假定任意App都有这些工具。[P08](https://developer.android.com/ai/appfunctions)。

对照：全串行、固定并发上限、工具资源分类的简单错峰、MARS式联合准入、KV管理单独优化、普通前台优先。主测任务完成时延、成功率、真实峰值内存、工具等待、前台帧质量和能量。一个GUI前台加后台工具是合理起点；多个GUI Agent同时抢同一个前台窗口会引入动作冲突，不能把这种不自然冲突当成推理调度收益。

**停止条件**：合理任务中工具太轻；模型和工具本来不重叠；全串行或固定并发策略已足够；收益只来自刻意低内存或人工延长工具耗时；或者方法等价于MARS的手机移植。这些情况下应转为工程组件或测量论文的一部分。

## 3. 方向三：进程被终止之后，恢复任务而不只恢复对话

**优先级：B。** 问题真实，但和已有恢复、持久化、状态胶囊工作重叠较多。只有恢复成本或一致性错误足够突出时才投入。

### 3.1 问题的准确边界

移动OS可以在内存压力和生命周期变化中终止进程；不能指望总能在被终止前得到保存回调。模型runner、Agent进度、工具实际状态也不一定同时存活。[Android官方文档，P10](https://developer.android.com/topic/performance/memory/guide/service-bindings)。

假设工具已经完成“创建记录”，但确认结果尚未写入Agent日志，服务就被回收；重新生成同一个工具调用可能重复创建。相反，保留了完整KV也不能证明外部动作尚未执行。

拟研究的窄问题是：**在手机内存和持久化成本约束下，怎样选择一致的恢复边界，将“必须耐久的语义进度”与“可丢弃重建的加速状态”分开处理。**

### 3.2 已有工作与不能夸大的保证

LangGraph已提供持久化检查点，MOBIMEM已有中断恢复，ClawVM处理驻留与持久性，Execution-State Capsules支持完整模型状态快照；ACRFence更直接指出恢复与工具重试中的语义风险。[P11](https://docs.langchain.com/oss/python/langgraph/persistence)、[A02](https://arxiv.org/abs/2512.15784)、[A10](https://arxiv.org/abs/2604.10352)、[C18](https://arxiv.org/abs/2606.20537)、[A11](https://arxiv.org/abs/2603.20625)。

因此不是“给Agent增加checkpoint”。[Agentic Transaction，A20](https://arxiv.org/abs/2608.13900)也已将工具效果、执行证据与恢复元数据纳入语义事务框架。差异必须落在Android生命周期、有限存储、NPU可恢复状态和外部工具效果的联合边界；泛化的“Agent需要ACID”不再作为候选贡献。

对于没有幂等键、事务或结果查询接口的外部工具，**无法仅凭本地日志普遍保证恰好一次副作用**。结果未知时应记录不确定状态并查询／暂停，不能自动重试后宣称已解决一致性。模型版本、量化、模板或运行时变动时，二进制快照也不应未经校验复用。

### 3.3 最小方法和评测

记录工具意图、调用ID、结果及提交状态，保存可验证语义进度；模型状态按版本指纹和重建成本选择保留。第一版只在轮次／工具安全边界保存，不追求任意token快照。缺少QNN状态导出接口时，日志＋冷重建仍是完整且必要的基线，不应先花几周造通用快照层。

AppWorld或ToolSandbox可提供可检查数据库终态；在工具前、工具完成未记账、记账后、模型生成中注入故障，分别杀Agent进程和runner，再显式重启。增加真实切后台及合理内存压力测量，区分可控故障注入与自然发生率。`force-stop`后的重新启动条件必须按Android机制处理，不能假设服务会自行复活。[B03](https://github.com/StonyBrookNLP/appworld)、[B04](https://github.com/apple-aiml-research/ToolSandbox)。

基线：无恢复、仅持久化文本与工具日志、每轮全状态保存、只保存KV、状态大小／重建成本启发式。主指标：终态正确、重复或丢失工具效果、恢复完成时延、保存开销、写入字节和模型重载次数。

**停止条件**：幂等工具＋每轮日志已解决正确性且恢复很快；或者重载权重完全主导、保存推理状态无显著价值。若收益只有完整KV快照，应按状态管理工作定位，不能包装成新的Agent恢复问题。

## 4. 方向四：手机热预算应分给哪些步骤，才能完成更多有用任务

**优先级：B，和已有slack reclamation方向衔接，但不应按原宽泛题目直接推进。**

### 4.1 仍可能值得问的问题

一次解码每token更省电，不代表任务总体更省：小模型或低能力执行可能产生更多错误与工具重试；前面持续高性能也可能挤占后续需要及时执行的步骤。候选问题是：**当热状态具有跨步骤记忆时，逐请求满足时延约束的策略，是否仍会损害整条任务的成功率或完成数量？**

持续负载测量已揭示手机热与性能差异；PELM联合频率、推测和深度，AgentStop预测低价值轨迹并早停，When Is Smaller Greener分析模型可靠性和任务长度的资源交叉点。手机NPU上的测试时计算扩展也已有直接工作；不能把“热”“节能”“按成功任务计量”任一项单独当作创新。[I19](https://arxiv.org/abs/2509.23324)。[I12](https://arxiv.org/abs/2603.23640)、[I13](https://arxiv.org/abs/2609.09662)、[C13](https://arxiv.org/abs/2605.15206)、[A14](https://arxiv.org/abs/2610.19345)。

### 4.2 怎样收窄才合理

先只选一个模型和少量真正可切换的运行配置，不做任意换模型、切量化、改推理深度的大组合。Agent提供任务阶段、剩余交互的粗估计、是否要进行高成本验证；服务侧提供热余量和配置成本估计。比较：始终高性能、始终低功耗、固定间隔、逐请求deadline策略、温度阈值策略与跨步骤预算。

一旦扩展到模型或提示预算，必须增加[ElastiLM，C24](https://xumengwei.github.io/files/MobiCom25-ElastiLM.pdf)式的请求SLO弹性基线；一旦使用DVFS，则对照[DVFSLM，I20](https://scholars.cityu.edu.hk/en/publications/energy-efficient-small-language-model-inference-for-mobile-agents/)的功耗—时延建模思路。否则容易把已有的单请求配置选择重新命名为Agent预算控制。

若研究推理预算或验证次数，还必须把能力改变与调度改变分别归因。`/no_think`、提前截断或减少反思可能改变策略和成功率；不能只报告时延下降。不要把用户耐受时间随意设成一个刚好让方法获胜的常量，至少报告多个预算下的成功—能量—时延曲线。

### 4.3 可用评测和停止条件

用能稳定闭环的AppWorld／ToolSandbox任务或AndroidWorld子集组成持续到达流，使用真实手机、被动散热、固定环境，记录完整失败和重试。热效应要用持续轨迹，冷启动之间的恢复也要有规则；瞬时吞吐和十分钟后吞吐不能混用。[B01](https://github.com/google-research/android_world)、[B03](https://github.com/StonyBrookNLP/appworld)、[B04](https://github.com/apple-aiml-research/ToolSandbox)。

**停止条件**：合理负载下NPU没有显著热积累；固定低功耗或简单温度阈值已达到同等成功—能量边界；所谓节能主要来自删掉困难任务；或者跨步骤信息在控制模型能力后没有增量。root/DVFS不可用时，只使用公开的性能模式、线程数、段大小等已验证旋钮，不能承诺实际不存在的控制能力。

## 5. 本轮不建议作为独立主线的题目

| 宽泛想法 | 淘汰理由或需要补的关键条件 |
|---|---|
| ready-aware／tool-aware KV替换 | InferCept、Continuum、MARS已有高度相关设计；你现有实验还必须扣除close收益 |
| 将Agent任务映射为DAG并调度 | Parrot、Ayo、Autellix已有；真实Agent未来路径又不完全可知 |
| 提供Agent Service与推理层新API | Pie、AIOS及多种产品接口已有；API应是解决具体瓶颈的机制 |
| 工具schema跳过JSON固定token／并行参数 | SGLang和SchemaWeaver已有直接先例 |
| 预测下一屏、提前运行下一步 | PastForward已直接研究；必须有新的适用条件或不同问题 |
| 只做前后台Agent优先级 | Agent.xpu、Sereno及手机OS已有相关机制 |
| 等待工具期间释放NPU功耗请求 | Tandem已经包含，不能当成无人做过的发现 |
| 将所有历史压缩成任务状态 | AgentProg、MOBIMEM、ClawVM及大量上下文工作已覆盖 |
| 一般端云模型路由 | EcoAgent、SAIL等路线已有；还需要网络、暴露信息和切换成本的独特问题 |
| 多个GUI Agent在一部手机上任意并发 | 单一前台动作冲突可能使场景不合理；应先定义可并行的工具与任务 |
| 任意端侧Agent持续学习＋版本化KV | LOCAL已有先例，且手机训练可行性尚需单独证明 |

其中SAIL原始会议工作可见[MobiSys 2026目录](https://www.sigmobile.org/mobisys/2026/program/)。本报告未逐节审阅其全文，因此仅把它用于排除“端云协同没人做”的宽泛说法。

## 6. 建议你现在做的选择

先用两轮小试回答两个是／否问题：**现有手机闭环有多少计算在依据失效后继续发生？真正本地工具与LLM重叠时，简单串行或并发上限会损失多少？** 先看分布和失败原因，再决定方法。

如果两者都不明显，不要强行围绕现有runner造一个新调度器。可以保留它作实验基础，优先提升可闭环的任务覆盖与测量可信度；方向三、四也必须过各自停止条件后再立题。可发表的核心应是一个被证据支持的抽象失配，而不是系统中新增了多少模块。
