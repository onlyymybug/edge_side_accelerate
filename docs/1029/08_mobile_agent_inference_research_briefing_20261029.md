# 手机上的 Agent 与本地大模型：别人做了什么，我们还能研究什么

更新日期：2026 年 10 月 29 日。本文以手机相关工作为主，保留论文、代码和数据链接。实验结果来自相应作者；本次整理没有新增真机实验，也没有实际复现这些系统。

这份报告围绕一个问题展开：**手机上有多个 Agent 任务时，怎样安排它们使用同一个大模型，才能让任务更快完成？**

先看一个手机助手的例子。用户说“找到明天下午的空闲时间，帮我创建一个提醒”。Agent 可能先让模型决定查什么，再调用日历工具，收到结果后再次调用模型，最后创建提醒。完成一个任务，往往要交替经历多次模型推理和工具执行。

这里有两个分工：**Agent Service 负责推进任务**，决定查什么、调用哪个工具、任务是否完成；**LLM Inference Service 负责运行模型**，接收输入、排队计算、返回输出。你的方向关注两者之间的配合：模型服务收到不同任务的请求后，应该先处理哪个。

读论文时，要区分三件事：

- **模型在手机上推理**：计算由手机完成。
- **任务在手机上执行**：点击 App、查询本地数据或执行工具发生在手机上。
- **完整任务在手机上完成**：模型反复推理、调用工具、读取结果，直到完成用户目标。

这些事情可以分开。一些论文让手机运行模型，让电脑模拟器执行操作；另一些项目让手机执行工具，却调用云端模型。下面会说明各项工作的情况。

## 1. 现有工作：别人已经解决了哪些问题

### 1.1 让手机上的模型运行得更快、更省资源

这一类工作首先面对的是：手机内存有限、计算能力有限，持续计算还会发热。怎样把模型跑起来，并减少一次推理的时间和耗电？

| 工作 | 它在解决什么问题，用了什么办法 |
|---|---|
| [llm.npu，ASPLOS 2025](https://arxiv.org/abs/2407.05858) | 手机 NPU 是专门加速神经网络的处理器，但不能直接高效运行所有大模型计算。论文通过拆分输入、处理特殊数值和分配计算，让手机 NPU 更好地执行模型。 |
| [PowerInfer-2，2024 预印本](https://arxiv.org/abs/2406.06282) | 大模型可能放不进手机内存。论文利用每次计算实际只需要部分神经元的特点，安排数据加载和计算，在手机上运行更大的模型。 |
| [HeteroInfer，2025；早期名称 HeteroLLM](https://arxiv.org/abs/2501.14794) | 手机 CPU、GPU、NPU 各有擅长的计算。论文研究怎样把模型计算分给这些处理器，提高执行效率。 |
| [PowerBench，2026-07，10 月更新](https://arxiv.org/abs/2607.05475) | 同一个模型换一种手机推理框架，速度和耗电可能差很多。该工作在多款高通手机上测量这些差异，帮助定位时间和能量究竟花在哪里。 |

**这一层已有较多研究。**“在手机上部署一个模型”通常只是实验基础。如果研究 Agent 调度，还需要说明多个任务出现后，新增了什么问题。

### 1.2 多个应用共享手机模型时，怎样管理资源

这一类更接近你的方向：除了模型计算，还考虑多个应用、会话或前后台活动之间的配合。

**Libra：切换会话时，怎样避免重新计算太多内容。**

假设聊天、邮件助手和日历助手共用一个手机模型。模型权重可以共用，但每个会话都需要保存自己的历史计算结果。这些结果通常称为 **KV Cache**，帮助模型接着前面的内容继续计算。会话多了，缓存可能放不下；先移到存储中、之后再加载，也会花时间。

[Libra，SenSys 2026](https://doi.org/10.1145/3774906.3800479)通过压缩、保存、加载和重新计算这些状态，降低会话切换成本，实验包含小米 14。它主要回答“切回一个会话怎样更快”，而你的问题还包括“现在应该先服务哪个任务”。

论文主要使用新闻分类、摘要、翻译等 NLP 数据构造调用记录，记录调用时间、会话编号和输入等信息。“72 小时轨迹”指记录中的时间跨度，并不是采集了用户连续使用手机 72 小时的 Agent 行为，也不等于运行了 72 小时的完整 Agent 任务。

**ElastiLM：不同请求需要不同响应速度，怎样分配计算量。**

后台整理记录可以慢一些，用户正在等待的回复需要快一些。如果所有请求都使用同样大小的模型和同样长的输入，就不容易同时满足要求。

[ElastiLM，MobiCom 2025](https://xumengwei.github.io/files/MobiCom25-ElastiLM.pdf)根据请求的时间要求，选择多大的子模型，以及保留多少输入内容，目标是在满足速度要求时尽量保住回答质量。它主要决定“这次请求花多少计算”，而你的问题首先是“下一次先处理谁的请求”。

论文在三款手机上实验，服务负载包含从六个数据集抽样组成的 600 个请求。表中的 Gmail、Gboard 等名称代表作者设定的应用需求类别，不能理解成这些真实 App 都在手机上运行并完成了任务。

**Sereno：后台模型计算时，怎样让前台应用仍然流畅。**

手机一边运行模型，一边播放视频或操作 App 时，两边可能争用内存带宽等资源。[Sereno，OSDI 2026](https://www.usenix.org/conference/osdi26/presentation/xin)安排后台推理在适当位置暂时让出资源，减少前台卡顿。它关注模型与前台应用共存，而不是多条 Agent 任务中先完成哪一条。

**Android NPU Manager：由系统管理多个应用的 NPU 使用。**

[Android NPU Manager](https://source.android.com/docs/core/perf/npu-manager)是 Android 17 的系统机制，涉及模型能否加载、优先级和资源紧张时如何卸载或暂停。能否使用它，要看手机和厂商是否支持。它提供资源管理能力，官方说明没有给出根据 Agent 后续步骤安排完整任务的算法。

这几项分别解决了：**切换更快、一次计算多少、前台是否卡顿、系统如何分配 NPU 资源。**它们与调度有关，但研究目标各有不同。

### 1.3 手机 Agent 怎样减少完成任务的时间

下面几项工作利用 Agent 的特点减少开销。AutoDroid-V2、MobileExplorer、PastForward 和 Tandem 涉及 GUI 任务；SchemaWeaver 主要评估工具调用生成。

下面保留模型配置，供后续复现时查用：2B、4B、8B 分别表示大约 20 亿、40 亿、80 亿个模型参数；4-bit、8-bit 是压缩模型数值的存储方式。理解各项工作的思路时，可以先跳过这些配置细节。

**AutoDroid-V2：让模型生成操作脚本，减少反复询问模型。**

传统 Agent 每操作一步，都可能再问一次模型。打开 App、进入设置、找到选项、修改设置，就可能需要多轮推理。

[AutoDroid-V2，MobiSys 2025](https://arxiv.org/html/2412.18116v3)先整理 App 的操作文档，再让小模型生成包含多个操作的脚本，交给程序执行。这样，一次调用可以推动多步操作。

- 手机延迟实验主要使用微调后的 **Llama-3.1-8B，8-bit**，通过 llama.cpp 在一加 ACE 2 Pro 上运行。
- 模型主要读取文字文档，不必直接识别截图。论文还比较了 Llama-3.2-3B、Qwen2.5-7B 的任务能力。
- [代码已公开](https://github.com/MobileLLM/AutoDroid-V2)，包含文档和数据生成、任务验证等内容；[最小示例](https://github.com/MobileLLM/AutoDroid-V2/blob/main/README_minimal.md)采用电脑模拟器。接入手机推理仍需配置和改造。
- 论文分别报告任务能力和手机推理延迟，不能把所有实验都说成“全部组件在同一手机上执行”。

**MobileExplorer：模型思考期间，先探索可能有用的页面。**

手机模型推理可能需要几十秒，而点击一个入口、读取页面、返回，通常快得多。[MobileExplorer，2026-05](https://arxiv.org/html/2605.26546v1)利用这段时间探索相关页面，把发现的信息交给后续推理，减少盲目尝试。

关键难点是：探索会改变界面，必须尽量恢复原来的页面，才能正确执行模型针对原页面给出的操作。它主要改变 **Agent 的执行流程**。

- 主实验使用 **4B 视觉语言模型**，引用指向 Step-GUI 技术报告；正文未给出完整模型版本名称。另有 MAI-UI-2B、8B 补充实验。
- Galaxy S24 上用 Q8 量化和 llama.cpp 推理；主要 AndroidWorld 任务在电脑模拟器上执行。
- 另有实体手机案例：在 Trip App 中搜索十个城市的景点；执行任务时插入通知、闹钟、来电等干扰；播放视频或音乐时切换蓝牙、Wi-Fi。干扰任务的名称在表格和正文中不一致，分别写成 Notes 输入任务和秒表任务。
- 暂未找到官方代码。论文写明接收后发布，当前可确认的是演示视频。

**PastForward：过去做过的操作，能否帮助下一次更快计算。**

不同任务可能包含相似输出和页面跳转。[PastForward，2026-09](https://arxiv.org/html/2609.32166v1)记录这些经验：生成答案时，把旧输出当作候选，让当前模型检查；执行当前操作时，预测下一屏并提前计算。预测正确才保留结果，预测错误就放弃。

- 手机使用 **Qwen3-VL-2B-Instruct**，在 Galaxy S26 Ultra、Xiaomi 15 上运行；语言模型权重为 Q8_0，使用定制 Android llama.cpp 和 NPU。
- AndroidWorld 及模拟器在独立电脑上。论文中的 Qwen3-VL-8B、GUI-Owl-1.5-8B、MAI-UI-8B 是服务器实验配置。
- 暂未找到官方实现和完整实验任务清单。

**SchemaWeaver：生成函数调用时，能否同时生成多个参数。**

模型调用工具时，需要输出函数名和参数，例如 `get_weather(city="北京")`。很多格式字符已经由工具定义确定，每个参数也有自己的格式要求。

[SchemaWeaver，2026-10](https://arxiv.org/abs/2610.17436)利用这些已知结构，减少逐个生成 token（模型处理文字的基本单位）的计算，并让部分参数同时生成。

- 在一加 12R 和 Pixel 7 上测试 Qwen3、Llama-3.2、SmolLM2 等 0.6B–4B 模型。
- 使用 BFCL-v4 的单轮调用子集和 DroidCall，主要测调用生成的耗时、正确率、内存与能耗。
- **手机上确实运行了模型，但这些结果不能说明完整任务已在手机完成。**生成正确的天气查询调用，不等于已经查到天气、读取结果并完成后续任务。主要时间指标也没有覆盖完整工具执行和后续 Agent 循环。
- 暂未找到官方修改版代码。论文说明基于 llama.cpp 实现。

**Tandem：针对手机 GUI Agent 的请求特点，修改推理引擎。**

Agent 每一步可能只改写一小段历史，输出也常常只是很短的操作指令。[Tandem，2026-10](https://arxiv.org/html/2610.26660v1)针对这些特点，改进历史计算结果的保存与恢复、多 token 校验，以及任务间歇时的 NPU 功耗管理。

它主要修改 **推理引擎**，与 MobileExplorer 改变 Agent 流程的做法不同。

- 主模型为 **LoRA 微调的 Qwen3.5-4B，Q4_K_M**，在一加 13T、一加 15 的高通 NPU 上运行。
- 输入主要是界面文字，必要时附截图。实验既有录制请求和 AndroidControl 样本，也有 17 个 App 中的 **100 个真机在线任务**。
- [代码已公开](https://github.com/flyingdoog/tandem)，主要是 llama.cpp 分支和 NPU 后端修改。尚未确认完整 Agent App、自建任务和所有轨迹均已公开。
- 部分主要延迟实验使用风扇散热，持续运行时还需单独看自然散热下的表现。

这些工作说明：**减少模型调用、把部分操作同时进行、复用历史计算，已经有人在手机 Agent 上研究。**新的调度方法需要找到更具体的损失。

### 1.4 非 GUI 任务和手机 Agent 项目

GUI 任务通过界面操作 App，例如点击、输入和滚动。非 GUI 任务通过工具或程序接口操作，例如直接读取通知、查询日历数据、执行数据库搜索。

**GUI Agent 也可以使用文本模型。**Android 能提供界面的结构化信息，通常称为无障碍树。它可能告诉程序“这里有一个文字为登录、可以点击的按钮”。转成文字后，普通 LLM 也能决定点哪个元素。无障碍树不是截图识别结果，能提供多少信息取决于 App；图片内容和缺少标签的控件可能还需要视觉模型。

| 工作或项目 | 能做什么，已经验证到哪一步 |
|---|---|
| [DroidCall，EMNLP Findings 2025](https://aclanthology.org/2025.findings-emnlp.484/) | 约一万条 Android Intent 调用训练样本，将自然语言转为闹钟、日历等操作；主要评测函数名和参数是否正确。另有微调 PhoneLM-1.5B、通过 mllm 在手机本地推理的演示。 |
| [FunctionGemma / Mobile Actions](https://ai.google.dev/gemma/docs/functiongemma/model_card) | 用 270M 小模型把指令转为系统工具调用，可离线控制手电筒、创建联系人等。官方给出 Galaxy S25 Ultra 推理性能和调用准确率，未给出完整多 Agent 调度测试。 |
| [PokeClaw](https://github.com/agents-io/PokeClaw) | 手机 App 中有本地模型和工具执行流程。作者用 Gemma 4 E2B 在 Pixel 8 Pro 验证了剪贴板解释、通知总结、电池建议、存储分析四类任务；复杂 GUI 任务的另一组成绩使用云模型。 |
| [PalmClaw](https://github.com/ModalityDance/PalmClaw) | 公开手机会话、工具和任务管理代码；官方配置通过模型 API 获取结果，可以参考手机工具实现，但不能据此认定模型也在手机。 |

“非 GUI”不保证没有界面变化。例如，Intent 可以直接打开填好参数的页面，省去 Agent 逐个找按钮的过程，但有时仍需用户确认。

## 2. 最近的研究正在往哪里走

### 2.1 从“一个模型跑多快”，走向“多个应用怎样共用”

Libra 管多个会话的历史状态，ElastiLM 按请求的时间要求分配计算，Android NPU Manager 管应用之间的资源。研究开始考虑模型作为手机公共服务时会发生什么。

你的问题可以接在这里：**这些服务知道每次请求的情况，如果还知道它属于什么任务，能否安排得更好？**这需要实验验证。

### 2.2 从“每一步快一点”，走向“整个任务少做几步”

AutoDroid-V2 一次生成多步脚本，MobileExplorer 提前探索页面，PastForward 利用过去的经验。完成任务快不快，不能只看模型每秒生成多少 token，还要看总共调用多少次、重复做了多少事。

所以，你的实验应测“一条用户任务多久完成”，同时保留每次推理的时间记录，才能解释收益从哪里来。

### 2.3 让 Agent 的特点影响推理引擎设计

SchemaWeaver 利用函数调用的固定格式，Tandem 利用历史局部变化和短输出。模型服务已经开始针对 Agent 请求做优化。

因此，“两层交换信息”只是实现手段。研究贡献还要说明：**交换了什么信息，改变了哪个决定，解决了多大的实际问题。**

### 2.4 把前台使用、后台活动和发热考虑进来

Sereno 关注前台流畅度，MobileExplorer 测试后台视频和通知干扰，Tandem 关注模型常驻时的空闲耗电。真实手机还需要同时服务其他活动。

你的实验应选择有实际用途的任务组合，例如后台整理记录尚未完成时，用户又发起查询，不必假设用户会持续提交大量任务。

## 3. 哪些想法已经有人做，哪里还值得查

| 想法 | 已有相关工作 |
|---|---|
| 多个应用共用手机模型，切换时保留历史 | Libra |
| 根据速度要求调整模型大小和输入长度 | ElastiLM |
| 后台模型给前台应用让出资源 | Sereno、Android NPU Manager |
| 加快函数名和参数生成 | SchemaWeaver |
| 减少反复问模型，利用过去执行过的内容 | AutoDroid-V2、MobileExplorer、PastForward、Tandem |
| 在 Android App 中管理模型调用、工具和会话 | PokeClaw；PalmClaw 可参考手机控制部分 |

**在本次核查的手机文献中，尚未找到完整展示以下组合的论文：同一手机本地推理，多个独立 Agent 任务同时未完成，调度目标是让整条任务更快完成。**这可以作为继续调查和实验的起点。

要区分两种“还没做”：一种是缺少手机完整实验，另一种是现有调度方法确实解决不好手机上的新问题。要证明算法有新意，还需要与其他平台已有的任务调度思路比较。当前报告只保留手机相关工作，不替代这一步查重。

## 4. 可以研究什么，先怎样判断问题是否存在

### 4.1 首选：多个任务都要用模型时，先处理谁

**先看一个例子。**手机模型一次处理一个请求，每次需要 10 秒，暂时忽略工具时间。任务 A 要调用模型三次，任务 B 只要一次。两个任务同时到达。

| 执行顺序 | B 什么时候完成 | A 什么时候完成 |
|---|---|---|
| A 第一次 → B → A 第二次 → A 第三次 | 第 20 秒 | 第 40 秒 |
| B → A 第一次 → A 第二次 → A 第三次 | 第 10 秒 | 第 40 秒 |

模型计算总量一样，只换了顺序，B 就提前完成，A 也没有变慢。这个例子只是说明执行顺序有影响；“短任务先做”本身是已有的简单方法。

**真实任务为什么更难？**系统通常不知道一个任务还要问模型几次。任务可能中途等待工具，回来后再次排队。切换任务还可能需要恢复上下文；优先处理用户查询，也可能让后台任务一直等。

因此，想研究的是：**面对这些情况，手机上的简单排队方法哪里表现不好？Agent 提供的信息能否帮助改善？**

**第一步先做什么？**固定模型、输入内容和 Agent 的做事方法，只改变请求执行顺序。标明每个请求属于哪个任务，记录任务何时等待工具、何时可以继续，以及上下文恢复需要多久。先不同时改模型大小、提示词和任务目标，避免分不清收益来自哪里。

“等待工具时暂时不分配模型”是基本功能，不足以单独成为新方法。更值得找的是真实取舍：例如先恢复用户查询会多花一点时间，却可能显著减少用户等待；继续当前任务省去切换，却可能让其他任务迟迟结束不了。

**和哪些简单办法比较？**

| 办法 | 用直白的话说 |
|---|---|
| 请求先来先处理 | 哪次模型调用先排队，就先执行哪次，通常称为请求级 FIFO。 |
| 按任务轮流处理 | A 用一次，再给 B 一次机会；没有可执行请求的任务跳过。 |
| 尽量先完成早到的任务 | 两个任务都有请求时，优先推进更早到达的任务。它等待工具时，其他任务可以用模型。 |
| 用户正在等的任务优先 | 前台查询先做，后台整理稍后做。 |
| 优先选择恢复开销小的任务 | 在其他条件相同时，先做上下文已在内存中或恢复较快的任务。 |

各策略采用相同模型和缓存管理。任务结束后都释放不再需要的状态；腾空间时，还应与“先移走最近最久没用的状态”比较，这种常见方法叫 LRU。如果引擎只能在一次请求结束后切换，各策略都使用这个切换位置。

**任务从哪里来，怎样测？**从 AndroidWorld 或 DroidTask 选多步任务，让 Agent 实际执行，再规定第二、第三个任务什么时候加入。任务内容可以复用，到达时间需要自己设置，并说明这是一组受控实验。

记录排队、模型计算、上下文恢复、工具执行和等待界面的时间。最终比较：平均任务完成时间，最慢一批任务的等待，固定时间内完成的任务数，有没有任务长期得不到服务，以及成功率和耗电。

**什么时候值得继续？**如果只改执行顺序，就能在成功率相当时稳定缩短完成时间，而且简单方法仍有明显损失，就有理由继续设计算法。如果简单方法已经很好，或时间主要花在调度无法改变的等待上，就先保留测量结论，重新判断研究重点。

目前最建议先做这项测量。**已有明确的问题形式，但还没有实验结果证明需要新算法。**

### 4.2 次选：手机工具需要内存时，要不要先移走模型保存的状态

**一个例子。**任务 A 等工具时，模型服务保留了它的历史计算结果。任务 B 要做本地图片文字识别或文档检索，需要加载模型、索引或临时数据。内存不够时，B 可能启动不了，或者变慢。

可以研究：应该继续保留 A 的状态，还是先腾出内存给 B，之后再付出恢复 A 的代价？

**先确认冲突真的存在。**读取电池、通知或少量日历数据可能很轻，非 GUI 工具不一定比 GUI 任务占资源。真正占空间的可能主要还是共享模型和各任务的上下文。

要先测工具峰值内存、执行时间，以及删除会话后实际释放了多少内存。不能只根据“工具很多”就认定冲突严重。工具在电脑运行时，也不能用它的内存曲线说明手机上的冲突。

**先和简单办法比较。**例如为工具固定留一部分内存、及时释放已结束任务的状态、按 LRU 移走旧状态，或者限制同时接纳的任务数。这些仍解决不好时，再研究根据工具需求和恢复代价做选择。

这项需要扩展手机本地工具与任务，不能直接拿原始 AndroidWorld 完成验证。修改日历、发送信息等操作，也不能靠重复执行来随意“重算”。

### 4.3 备选：连续执行任务后，发热会不会改变好的执行顺序

**一个例子。**手机刚开始运行时，全速执行可能最快。持续运行后温度升高，处理器可能降低频率，后面的任务反而变慢。需要验证：某种短时间看更快的安排，会不会让整组任务最后完成得更晚。

先在有实际用途的持续任务中记录温度和速度，再比较固定配置、简单温度阈值控制、前台优先等办法。使用同一批任务、相近的环境温度，并统计失败尝试的耗电。

如果任务短，不会明显发热，或简单控制已经足够，就不需要继续扩大。现阶段它是备选，优先级低于 4.1。

## 5. 哪些数据和代码可以拿来用

### 5.1 可以执行的任务，和只能读取的示范，要分开选

调度可能改变执行过程。要测任务最终是否完成，最好有可执行环境，以及判断结果对错的办法。只有过去录制的截图和动作时，更适合测推理速度和状态复用，不能直接当作新的在线任务结果。

### 5.2 第一阶段和真机阶段分别测什么

**第一阶段：手机运行模型，电脑提供独立任务环境。**

例如在电脑开两个模拟器，分别执行 A、B，都请求同一手机模型。这样可以先观察推理排队和上下文切换有没有损失。手机提供真实推理性能，但这套设置不能证明工具和模型在手机上争内存。

**真机阶段：模型和工具都在同一手机。**

这时还要处理界面和资源问题。同一手机通常只有一个供这些 GUI 任务操作的前台界面，A、B 不能假装各有互不影响的屏幕，需要规定谁能操作界面、什么时候切 App。轻量后台 API 任务通常更容易与其他任务重叠，但仍要实测。

如果先用非 GUI 任务，可以从能检查结果的查询、检索或记录整理开始。选任务时要检查它是否真的包含多轮推理和工具反馈；单次输出一个函数调用，不能充分验证多轮任务调度。

## 6. 建议先做出什么结果

先选少量能稳定完成、能检查结果的多步任务，接入同一个手机模型服务。实现先来先处理、按任务轮流、前台优先等简单方法，使用相同模型和状态释放办法。

第一轮实验最好回答四个问题：

1. 多任务时，有多少时间花在排队，而不是模型计算或工具本身？
2. 只调整模型请求的顺序，哪些任务提前完成，哪些被推迟？
3. 切换任务需要多少时间和内存，会不会抵消收益？
4. 让调度器知道任务信息后，能否比简单方法更好，同时保持相近的成功率？

如果能指出一个真实、反复出现的场景，说明简单方法为什么吃亏，再提出办法减少损失，论文的问题和贡献就会比较清楚。**目前最需要的是这组测量，而不是先给尚未验证的调度算法取名字。**
