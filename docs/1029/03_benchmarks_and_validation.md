# Benchmark选型与判别实验：先证明问题，再设计系统

> **2026-10-29更新提示：** 本文保留原实验协议；候选方向的当前覆盖关系和优先级见[新版汇报稿](08_mobile_agent_inference_research_briefing_20261029.md)，其中已撤回通用版本化取消／状态继承作为独立新主线的推荐。

截止2026-10-27。以下均为建议协议，未实际安装验收新benchmark，也未新增手机实验。原始资源见[注释目录](04_annotated_sources.md)。

## 1. 哪些benchmark可以直接用，哪些只能借一部分

“有公开benchmark”不等于“已有这个系统问题的完整负载”。应拆开：任务语义、可执行环境、正确性checker、自然时序与资源消耗。这五项通常来自不同资源，拼接后必须公开改动。

| 资源 | 闭环与评估能力 | 适合本次哪些问题 | 必须补什么／不能证明什么 |
|---|---|---|---|
| [InterruptBench（2026-10-28补查）](https://github.com/HenryPengZou/InterruptBench) | WebArena任务的中途要求更新、回放与终态评估 | 用户改口／撤回、长任务适应与修复 | 原协议按动作序号／轨迹进度注入，不是手机运行中取消；需另加墙钟与执行阶段事件，详见[补充报告](06_interruption_datasets_update_20261028.md) |
| [AndroidWorld，B01](https://github.com/google-research/android_world) | Android模拟器内运行任务，有参数化状态检查 | 失效传播、GUI闭环；手机推理＋模拟器工具的第一阶段 | 116类任务不等于116个独立用户；默认任务不含完整连续时钟／取消协议；模拟器不提供真机热与App负载 |
| [AndroidLab，B02](https://github.com/THUDM/Android-Lab) | Android交互与评估框架 | 第二环境、避免只适配一个任务集 | 需冻结App版本、初始化、账号与网络；不假定全部任务可无修改迁移真机 |
| [AppWorld，B03](https://github.com/StonyBrookNLP/appworld) | 可执行API、应用数据库和任务单元测试 | 多步API Agent、工具效果、状态恢复；与你现有代码最兼容 | PC工具耗时不是手机工具耗时；原始Agent可交互写代码，裁剪工具的function-call版本是派生设置 |
| [ToolSandbox，B04](https://github.com/apple-aiml-research/ToolSandbox) | 有状态工具、用户模拟器、中间里程碑 | 意图更新、隐式前提、设备设置语义、恢复终态 | Python模拟器并非Android系统API；用户模拟器模型与延迟需要记录 |
| [BFCL V4，B05](https://gorilla.cs.berkeley.edu/leaderboard) | 包含多类函数与Agent评测子集 | 模型调用能力、格式、长上下文、少量状态依赖分析 | 必须指定子集；静态AST／参考历史不能替代任务环境真实执行 |
| [HammerBench，B06](https://github.com/MadeAgents/HammerBench) | 多轮槽位与意图变化等对话评测 | 筛选意图更新场景、验证参数传递 | 不自带自然并发与完整手机工具时间；不能把参考对话当在线Agent轨迹 |
| [MobileWorld，B07](https://tongyi-mai.github.io/MobileWorld/) | 跨App、用户交互、MCP增强任务 | 更接近完整Agent Service的第二验证域 | 接入比初始小试重；必须记录用户模型与MCP服务是否远端 |
| [AndroidControl，B08](https://arxiv.org/abs/2406.03679) | 离线人类演示 | 观察／动作输入规模、单步质量、推理回放 | 不能直接测策略改变后的闭环成功率、过期动作或重试 |
| [MobileAIBench，B09](https://github.com/SalesforceAIResearch/MobileAIBench)、[MLPerf Mobile v6，B10](https://mlcommons.org/2026/06/mlperf-mobile-v6/) | 部署能力、基础质量和性能 | 后端与模型初筛、基本性能参照 | 不替代多步Agent与动态环境 |
| [DynamicGUIBench，B11](https://arxiv.org/abs/2604.25380)、[LivingScreen，B12](https://github.com/BITHLP/LivingScreen)、[DynaCU-Bench/AOI，C20](https://github.com/19PINE-AI/aoi) | 动态GUI与连续观察 | 失效与观察成本机制验证 | 平台不同；浏览器任务不自动变成Android原生任务，需要额外真机域 |
| [AppSim，B13](https://github.com/Acrab-Agentic-Labs/AppSim) | 可控模拟App、可复现后端状态；README提供Android环境配置 | 受控GUI实验与版本／数据变化 | 模拟App的内存、I/O与渲染负载未必代表原商业App |
| [AndroidReality，B14](https://github.com/Xiao0o0o/AndroidReality) | 界面状态、动作和转移扰动及恢复工具 | 弹窗、延迟、丢动作等受控扩展 | 早期研究代码，未运行；不假设它已实现NPU runner或进程死亡恢复 |
| [MemGUI-Bench，B15](https://arxiv.org/abs/2602.06075) | 动态任务中的语义记忆与跨会话能力 | 检查语义进度保留是否有质量影响 | 不直接判断KV合法性或二进制状态可恢复性 |
| [Async-RBench，B17](https://github.com/pope8zdt/Async-RBench) | 异步返回后的更新／保留／重新验证 | 对异步结果有效性做补充语义测试 | 并非手机系统负载，不能凭它测NPU争用 |

推荐起步组合：**现有AppWorld用于闭环与恢复小试；AndroidWorld＋受控扰动用于动态观察问题；真正本地工具任务用于资源问题。** 不建议一开始同时接入十个benchmark。

## 2. 为每种结论设一个证据层级

| 层级 | 做法 | 能回答的问题 | 不允许推广的结论 |
|---|---|---|---|
| E0：静态回放 | 相同输入、固定输出或参考轨迹 | 模型阶段成本、同一序列下KV替换的机制差异 | Agent真实成功率、改变时延后的轨迹、自然并发 |
| E1：手机推理＋主机环境闭环 | Agent按实际模型输出执行AppWorld或模拟器工具 | 任务质量、调度改变是否影响闭环、推理真机成本 | 工具也在手机、真实App内存争用、全手机能量 |
| E2：模型＋相关工具在真机 | 工具、模型、状态与资源监测在同一手机 | 统一内存争用、前台影响、热、生命周期成本 | 不经更多设备与负载验证就推广到整个Android生态 |

这不是要求所有论文都做到E2；是要求论文主张与证据范围一致。若研究问题是手机资源耦合，E1不够；若是API语义与推理队列的失效传播，E1可以作为可行性验证，最终仍需手机交互证据。

## 3. 结合你当前代码，先做哪些小试

### 3.1 先过模型能力和runner能力门槛

依据现有[周记](../weeks/1026.md)和[AppWorld小试记录](../reports/appworld_agent_kv_next_validation_20261026.md)：Qwen2.5-3B已能跑部分工具闭环，但出现实体ID选择和非法JSON问题；Qwen3-4B短版输出OK只证明基本推理，没有证明工具、多Session与6144上下文能力。这些是既有记录，不是本轮复测结果。

建议验收顺序：

1. 固定模型、量化、tokenizer、chat template、上下文上限和后端版本。
2. 用开发实例调通工具格式；另留未触碰的任务族／实例验证能力。若裁剪工具、预登录、归一化参数或修复JSON，要逐项公开。
3. 检查单任务与交错任务是否使用同一模型进程，Session独立性是否正确，close是否真的终止相关请求。
4. 测出取消粒度、图段耗时、能否读到logprob、能否保存恢复状态、性能模式是否真正改变执行，以及驻留内存如何变化。

不要为完成调度论文不断筛掉SLM做不好的任务，却将结果称为完整AppWorld。可以定义一个明确的可执行子集，但应公开全部候选、排除原因和失败日志，且不把开发实例算作新任务成功率。

模型能力不足时，可以用正确工具结果或参考动作作诊断上界，定位系统机制是否有空间；这仍是E0／oracle辅助，不能计为模型闭环结果。也不要用大模型在PC生成的正确轨迹替代手机Agent后声称成功率提高。

### 3.2 对方向一的最小记录

为每个事件保留：`task_id, intent_epoch, observation_version, event_type, host/device_time, request_id`；为每次推理保留入队、prefill开始、decode开始、取消请求、取消生效、返回和动作提交时间。

从以下三组分开开始：自然运行；固定时钟注入相同变化；每次策略内部事件触发的机制测试。第三种会随策略改变而改变环境，不宜与固定时钟测试混合解释。

先统计“依据已失效后仍执行的计算”占比及分布，按原因划分为用户更新、关键UI改变、数据版本改变、监测误报。再比较最新请求覆盖与执行前刷新。能接近oracle上界时就停止复杂策略开发。

### 3.3 对方向二的最小记录

先单独profile每种真实手机工具，再测它与prefill、decode及前台渲染的两两组合。记录重叠区间、峰值内存、耗时放大、CPU/GPU/NPU执行路径与输出正确性。

只有出现可重复的冲突，才引入完整任务流。用AppWorld工具等待时间映射成手机OCR耗时可以做敏感性实验，但这是合成负载，不能冒充真实应用行为。

当前多Session实验中，**逻辑KV槽位数不是物理内存预算**。QNN若为所有Session预分配缓冲，逻辑驱逐可能只让下一轮重算，未真正释放相应RAM；要分别测分配、驻留和实际可回收内存。若物理内存始终不变，只能声称重算／复用行为发生变化，不能声称避免真实内存压力。

## 4. 一套避免虚假收益的实验协议

### 4.1 工作负载与时间

- 同一组任务、同一到达协议、同一环境初态、模型随机种子及工具版本；策略顺序随机化或交替，避免热历史和运行顺序偏差。
- 区分**开放到达流**与**闭合并发流**。更快的系统在闭合负载里会更早触发后续请求，交错变化是效果的一部分，不应强制假装完全一致。
- 对静态世界可固定随机种子；对动态世界同时报告固定墙钟变化和轨迹依赖变化，不能只选择有利的一种。
- 工具耗时包含实际执行与I/O；人工等待单独标注并报告敏感性，主结论不能只出现在超长人工sleep。
- 单机App/数据库状态要隔离。不同AppWorld任务通常需要独立世界；一台GUI设备只有一个前台，不能将独立世界并发与共享前台并发混用。
- 主机与设备日志用时钟映射校准；本地duration用monotonic时钟，跨机器不能直接相减未对齐的时间戳。

### 4.2 成功率、时延和goodput

主要质量是**任务终态正确**，并增加方向特有的无过期动作／不重复工具效果指标。工具JSON合法率、单步准确率和完成步数是诊断指标。

任务时延分解为：

`T_task = queue + inference + tool + observe/verify + orchestration + recovery`。

原本会重叠的区间不能简单相加；既保留时间线，也报告关键路径。TTFT和tok/s可以解释原因，但用户等待的是可执行动作或整个任务完成，不能将所有任务优化成TTFT。

建议定义任务goodput：在给定完成时限与有效性约束下成功的任务数／观察时间。必须同时报告提交、接纳、拒绝、取消、超时和失败任务数；仅统计被策略挑中的容易任务会误导。

失败任务和未完成长任务不能从时延图里悄悄消失。成功任务的完成时延可单独报告，但要连同全任务成功率、超时率及截尾规则展示。

### 4.3 能量、内存与热

完整系统能量为 `E_all = ∫ P_device(t) dt`，应覆盖失败、重试、监测、工具、模型加载和所定义观察窗口内的空闲保持。主指标可以是 `E_all / N_success`，同时约束相同任务集和可接受成功率；否则直接停止困难任务也会看似高效。并发任务的能量归因可作诊断，不能把重叠区间全额分给每个任务再相加。

SoC后端能量归因与整机电池成本并非同一个口径。PowerBench提供更细的后端测量思路，但设备、采样接口和权限受限，不能预设每部Redmi都能使用。[I11](https://arxiv.org/abs/2607.05475)。

优先使用经验证的外部供电／功率测量或可用的系统能量计；电池电流电压可作为粗测，需说明采样率、单位、充电状态、噪声和积分方式。USB输入功率不必然等于电池放电功率。不要拿短任务中几个电量百分比变化得出精确节能结论。

内存区分模型权重、KV／递归状态、图／工作区、工具中间结果和App内存；区分虚拟地址、RSS/PSS、共享缓冲和实际可回收量。多个进程的RSS相加可能重复计算共享映射。

热测试记录环境温度、保护壳、屏幕亮度、网络和充电条件；分清表面温度、SoC传感器和电池温度。手机持续应用主张应以被动散热为主，主动散热最多用于隔离机制。达到预定状态或使用完整热轨迹，不能仅靠“每次冷却一分钟”假定初态相同。Tandem与持续负载研究都提示必须交代这些条件。[C12](https://arxiv.org/html/2610.26660v1)、[I12](https://arxiv.org/abs/2603.23640)。

### 4.4 必须有的强基线和消融

| 组件／信息 | 最低比较 | 主要排除的伪收益 |
|---|---|---|
| 生命周期close | LRU、LRU+close、你的完整策略 | 把“任务结束释放”算成智能替换算法 |
| ready／waiting | 固定同一轨迹的机制分析＋真实闭环；有／无ready信息 | 将排队顺位或交错顺序变化误归因于ready |
| 失效事件 | 最新队列覆盖、执行前刷新、取消即停、普通抢占 | 只打败没有取消能力的工程基线 |
| 工具资源信息 | 全串行、固定并发、分类错峰、MARS式准入 | 收益其实只来自限制过量并发 |
| 保存恢复 | 文本／工具日志、幂等工具、冷重建、全量状态 | 把普通持久化包装成新机制 |
| 热预算 | 固定低功耗、温度阈值、逐请求时限策略 | bandit/RL只是在学习几个固定配置 |
| 额外模型或监测器 | 开销全计入；与同等信息的简单规则比较 | 验证／预测器资源成本被漏掉 |

同等资源下难以原样移植服务器系统时，实现其**核心决策规则**作为基线，并明确称为适配版本；不能把它称为原作者完整复现，也不能选择性削弱其输入信息。

### 4.5 统计与选题停止

小试用于判断问题量级，不用于宣布稳定百分比。正式规模应由小试方差和目标效应决定；不要把某个固定样本数当作充分性保证。使用多个任务族、参数实例、到达种子和热初态，尽量做配对比较，给出置信区间和原始分布。

同一模板的多个参数实例通常相关；重采样宜以任务族／运行种子分组，不能把所有token当独立样本。若样本太少，不报告不可靠的p99；先给ECDF、范围和样本数。

在正式实验前预先写下：开发／验证任务划分、主要指标、允许的工具辅助、排除规则、停止条件和比较基线。现有三任务小试可以作为机制证据，但不应被反复调试后包装为独立测试集。

## 5. 建议的阶段产物

| 阶段 | 产物 | 进入下一阶段的条件 |
|---|---|---|
| 可行性 | 模型／后端能力表、未触碰任务验证与失败分类 | 至少存在足够稳定、覆盖不止一个简单模板的闭环任务 |
| 问题测量 | 无方法加成的原始时间线、资源／失效分布、简单基线 | 存在自然或有充分应用依据的受控场景损失 |
| 方法小试 | 最小契约、一个控制机制、必要消融 | 超过强简单基线，额外监测／恢复成本计入后仍有收益 |
| 扩展验证 | 第二任务域／模型／设备、边界与失败实例 | 收益不是人工等待、特殊到达或主动散热制造的 |

每个阶段都允许得出“不继续”的结论。尤其目前的逻辑KV容量和PC工具环境，应优先用来缩小问题范围，而不是直接扩大真机压力测试。
