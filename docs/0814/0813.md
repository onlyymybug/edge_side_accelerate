# 0813：B 部分实验结果分析

本文只分析 `docs/require_list.md` 中 B1–B11 标为 **OK** 的格子；标为“——”或“未跑”的格子、以及表外但本地存在的结果均不纳入。B3 没有标为 OK 的格子，任务书中也没有 B4、B6、B8、B9 条目，因此这些编号没有结果表。设备记号按任务书解释：D1 = OnePlus，D2 = Redmi。D 部分按要求暂不分析。

## 1. 统计口径与数据质量

- `tokens/s`：成功样本的 `decode_token_per_sec` 算术平均，越高越好。
- `J/token`：有效非负能耗总和除以相应生成 token 总数，越低越好。仅纳入 `measured_signed_battery_energy`、能耗有限且 `energy_j >= 0` 的样本。
- `EDP`：逐样本 `energy_j × inference_ms / 1000` 的算术平均，单位 J·s，越低越好；使用与 J/token 相同的有效能耗样本。
- 表中 `#1/#2/...` 是该指标在**同一设备、同一任务的同表配置内**的排名；tokens/s 降序，J/token 和 EDP 升序。不同设备、不同任务不混排。
- GSM8K 和 MATH-500 均使用当前 `math_benchmarks_v2_relaxed_prm800k` 重新读取已保存 completion 后评分；没有修改原始推理结果。GSM8K 使用宽松答案提取加数值等价，MATH-500 使用宽松答案提取加 PRM800K/SymPy grader。BFCL 使用官方 evaluator，HammerBench 使用实验保存的结构化评分。
- `energy per correct task under deadline` 定义为：该配置整批有效实测能耗总和 ÷ 在指定 inference deadline 内答对且有有效能耗的任务数。deadline 使用 `inference_ms`，不是含主机/ADB开销的 wall-clock 延迟。
- deadline 表的格子写作 `J/正确题数`。带 `†` 的值因运行失败、缺失测量或负能耗而不是全数据覆盖，只能视为 provisional，不能与完整覆盖值作严格结论。

主要数据质量问题如下：

1. B2 两组 MATH-500 都是 499/500 成功：budget-512 的 `math500_0276`、no-budget 的 `math500_0474` 因 `adb shell dumpsys battery` 15 秒超时失败；budget-512 的 `math500_0298` 还缺少可用 inference-window 能耗。
2. B1 OnePlus Qwen Balanced-256 有两条负能耗；B7 BitNet Burst 与 LowPowerSaver 各有一条 inference window 未被 telemetry 包围；B10 两模型各有一条负能耗；D1 HammerBench 多轮两模型各有两条无效能耗记录。
3. B11 标为 OK 的 **D1 OnePlus × BitNet × 单轮**在 `/home/lyyyy` 全盘未找到对应 `summary_metrics.csv`，标准目录也不存在，因此无法伪造或用表外结果替代。该格需要找回或重跑。
4. B10 Qwen 虽在任务表中记作 budget-256，但当前 Qwen BFCL handler 实际固定 `--seq_len 1024`，没有独立输出预算；曾出现单题生成 725 tokens。故下文将它标为“nominal 256”，其准确率有效，但与 BitNet 的物理 output-budget-256 不是严格同预算比较。

这一组预算相同，比较最干净：

- Qwen 两种 mode 的生成内容与正确率一致。LowPowerSaver 比 Burst 慢 31.3%，但 J/token 降低 35.1%、EDP 降低 17.9%，体现了明确的速度—能耗交换。
- BitNet 三种 mode 的 1319 条生成 token 数和重评正确性完全一致，都是 905/1319，因此差异可归因于运行模式。Balanced 不仅最快，而且 J/token 和 EDP 都最低：比 Burst 快 9.8%，J/token 低 43.0%，EDP 低 53.4%；比 LowPowerSaver 快 61.1%，J/token 低 21.3%，EDP 低 51.3%。Redmi 上 `kHtpBalanced(8)` 对这一长批次形成 Pareto dominance，`kHtpBurst(2)` 并没有给出最高持续吞吐。
- BitNet 三种 mode 的旧 summary 中 Burst/Balanced 曾显示 438/1319，而 LowPowerSaver 显示 905/1319；原因是前两组使用强制 `The answer is ...` 的旧 parser。统一重评后都是 905/1319，不存在 mode 导致准确率翻倍的现象。

未纳入的 BFCL 类别中，已确认的外部依赖阻塞为：

- `web_search_base`、`web_search_no_snippet`：官方实现要求 SerpAPI，当前没有项目 `.env`，也没有 `SERPAPI_API_KEY`。
- `memory_vector`：官方实现要求 `sentence_transformers`、FAISS 和 `all-MiniLM-L6-v2` embedding 模型；当前 `bfcl-phone` 环境中两个 Python 包均缺失，模型也未缓存。

其余未标 OK 的 non-live/live/multi-turn/memory 类别不在本次任务表的可分析集合内；这里不把“未要求运行”误写成“因外部依赖无法运行”。

难度相关结论：

1. 正确率随难度严格单调下降。Balanced-512 从 Level 1 的81.4%降至 Level 5 的11.2%；no-budget 从86.0%降至19.4%。模型能力而不是硬件吞吐是主要瓶颈，因为五个 Level 的 tokens/s 始终约14.84–14.91。
2. 难度越高，模型平均生成越长、EDP越高。Balanced-512 的 Level 5 EDP 是 Level 1 的2.33倍；no-budget 则为3.93倍。与此同时 J/token 基本稳定在0.025附近，进一步说明 EDP增长来自 token 数和推理时长，而非每 token 能耗恶化。
3. No-budget 对所有 Level 都提高准确率，提升分别为 +4.6、+6.7、+9.5、+14.1、+8.2 个百分点；Level 4 收益最大。但其 EDP 在每个 Level 都更高，且难题代价尤其明显：Level 5 从409.00增至797.53 J·s。
4. Budget-512 的 seq-stop 总数为230/499，no-budget 为86/499。更大的可用输出空间减少了被截断题目并带来准确率提升，但 no-budget 仍受总 `max_seq_len=1024` 限制；Level 5 仍有41题触顶，难题的上下文容量问题并未完全消失。

## 5. B 部分综合结论

- **最佳 Redmi GSM8K operating point 是 BitNet Balanced-512**：五种配置中 tokens/s、J/token、EDP和所有 deadline 能效均排名第一，重评正确率也最高（68.6%）。
- **OnePlus MATH-500 是明显的 accuracy–EDP trade-off**：no-budget 增加9.4个百分点准确率，但平均 EDP 增加70.2%；是否采用取决于是否允许更长延迟和更高任务能耗。
- **BFCL 应优先 Qwen**：BitNet虽吞吐高、单 token 能耗低，但官方正确率差距使其任务级能效明显落后。
- **HammerBench 两模型绝对正确率都低**，尤其 BitNet。仅看 tokens/s 会得出相反结论；energy per correct task 显示 Qwen 在单轮、多轮都更合适。
- 当前最重要的数据补口是 **D1 OnePlus × BitNet × HammerBench 单轮**，以及把 Qwen BFCL 真正实现物理 output-budget-256 后再做严格 B10 对照。
