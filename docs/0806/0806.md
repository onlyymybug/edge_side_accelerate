# Oneplus · BitNet-2B vs Qwen2.5-3B

设备：oneplus（PLQ110）。含 BFCL / GSM8K / MATH500 三个数据集，两模型并排（无 HammerBench）。
- BitNet-2B：BitDistiller w4a16，性能档 burst（gsm8k 为 runner-default，其余 burst）。旧版 runner（`LD_PRELOAD` + `--kv_updater ShiftPointer` + `--logits_scale/offset`），每 token 解码时间随 seq_len 增长。
- Qwen2.5-3B：w4a16-block16，性能档 balanced。新版 runner（`--shared_buffer`，seq_len 固定 1024，速度与 seq_len 无关）。

### BFCL（simple_python）

| 模型 | n | tok/s (中位) | tok/J | EDP (中位, J·s) | 正确率 |
|---|---:|---:|---:|---:|---:|
| BitNet-2B | 400 | 6.17 † | 7.37 † | 103.0 † | 29.0% (116/400) |
| Qwen2.5-3B | 395 | 14.95 | 32.40 | 3.1 | **84.0%** (336/400) |

`†` BitNet BFCL 的速度/能耗数据被污染：BFCL 运行时在设备 shell 内嵌了 `pace_sample` / `dumpsys thermalservice` 采样循环（每 0.5s 一次），math500/gsm8k 没有这段。因此 6.17 tok/s、tok/J=7.37、EDP=103 明显偏离 BitNet 真实水平，**不可用于速度/能耗对比**；正确率（29.0%）不受影响。
函数调用能力 Qwen 大幅领先（84% vs 29%）。

速度上 BitNet（19.18）快于 Qwen（15.05）；BitNet 出结果更早（5s 内已有 20 条答对，Qwen 为 0）。⚠️ 两模型正确率均受 token 预算截断影响（见文末说明），非真实推理能力。

能效 tok/J 上 Qwen（50.70）显著优于 BitNet（22.31）——Qwen 输出更长摊薄固定开销 + 新 runner 更省电。⚠️ 两模型正确率同样受截断影响。

### ⚠️ oneplus GSM8K / MATH500 的 token 预算截断说明

与 redmi 相同的 pipeline 问题，两模型都受影响：
- BitNet GSM8K：1084/1319 条 `generated_tokens` 顶到 127（=128 预算上限）。
- BitNet MATH500：289/500 顶到 ~257（=256 预算上限）。
- Qwen 两数据集与 redmi 一致（几乎全部顶满，96%+ 为 `missing_answer_marker`）。

因此 GSM8K/MATH500 的绝对正确率**不代表真实推理能力**，仅用于同截断条件下的相对参考；速度/能耗不受此影响。

# Redmi · Qwen2.5-3B 全数据集评测结果

设备：redmi（annibale）  模型：Qwen2.5-3B-Instruct，量化 w4a16-block16，性能档 balanced
运行时：QNN / ExecuTorch 新版 `qnn_llama_runner`（`--shared_buffer` + `--decoder_model_version qwen2_5`，seq_len 固定 1024，decode 速度与 seq_len 无关）。

## 1. 主指标（全部数据集）

| 任务 | n | tok/s (中位) | tok/J | EDP (中位, J·s) | 正确率 |
|---|---:|---:|---:|---:|---:|
| **BFCL** (simple_python) | 400 | 17.51 | 31.63 | 2.7 | **84.0%** (336/400) |
| **GSM8K** | 1319 | 16.81 | 39.19 | 24.7 | ⚠️ 1.1% (14/1319) |
| **MATH500** | 500 | 17.30 | 33.74 | 27.6 | ⚠️ 0.2% (1/500) |
| **HammerBench-单轮** | 654 | 17.44 | 28.85 | 1.9 | 5.7% (37/654) |
| **HammerBench-多轮** | 830 | 17.24 | 26.40 | 3.1 | 7.2% (60/830) |

正确率口径：
- BFCL：score header（官方 checker 结果，`accuracy / correct_count / total_count`）。
- GSM8K / MATH500：`summary.csv` 的 `score_correct`。
- HammerBench：`summary_metrics.csv` 的 `score_correct`（end-to-end，即 function + arguments 全部正确）。

速度取 `decode_token_per_sec` 的中位数，tok/J = Σgenerated_tokens / Σenergy_j，EDP 取 `edp_j_s` 中位数。

## 2. Energy per correct-under-deadline（J）—— 仅 GSM8K / MATH500

| 任务 | @5s | @10s | @20s | @30s |
|---|---:|---:|---:|---:|
| GSM8K | —(0) | 305 (14) | 305 (14) | 305 (14) |
| MATH500 | —(0) | 1865* (1) | 1865* (1) | 1865* (1) |

- 括号内 = 该 deadline 内答对的样本数；`*` = provisional（`deadline_summary.csv` 中 `valid_for_full_dataset_reporting=False`）。
- 5s deadline 内 0 条答对：这两个数据集单条推理普遍 >7s，5s 对它们无意义。
- deadline 指标只对 GSM8K / MATH500 报告（约定），BFCL / HammerBench 不适用。

## 3. 速度 / 能耗解读

- **速度极稳**：所有数据集 decode ≈ 17 tok/s。新版 runner 每 token 解码时间与 seq_len 无关，因此各数据集之间几乎无差异。
- **tok/J**：GSM8K 最高（39.19），因为它输出长（几乎每条都跑满 token 预算），固定开销被摊薄；HammerBench 输出短、prompt 长，tok/J 最低（26–29）。
- **EDP**：GSM8K / MATH500 比 BFCL / HammerBench 高一个量级（25–28 vs 2–3），因为单条 inference 时长长（输出 token 多 × 每 token 时间）。

## 4. ⚠️ GSM8K / MATH500 低分是 pipeline 截断，不是模型能力

**1.1% / 0.2% 不能当作真实推理准确率**，原因是输出被 token 预算切断，未走到最终答案：

- GSM8K：**1273/1319（96.5%）** 失败原因是 `missing_answer_marker`（输出中根本没出现最终答案标记）。
- **1314/1319 条 `generated_tokens` 顶到 127**（= `GSM8K_TARGET_OUTPUT_TOKENS=128` 上限）。推理链中途即被预算切断。
- 能成功解析出答案短语的仅 46 条，其中 14 条判对 —— **一旦输出完整，正确率 ≈ 30%（14/46）**，与截断后的 1.1% 是两回事。
- MATH500 同理（256 token 预算，`missing_boxed_answer` 类），只有 1 条完整输出到 `\boxed{}`。

这与 oneplus 上观察到的是同一类问题。BFCL / HammerBench 因输出短未受影响，那三项数字可信。

**结论**：要拿到 GSM8K / MATH500 的真实准确率，需把 `GSM8K_TARGET_OUTPUT_TOKENS`（≥256）、`MATH500_TARGET_OUTPUT_TOKENS`（≥512）调大后重跑；速度 / 能耗数据本身不受影响。
