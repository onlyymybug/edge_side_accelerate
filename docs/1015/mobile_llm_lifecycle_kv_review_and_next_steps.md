# 手机端多 Session KV 生命周期管理：现状评估与下一步建议

日期：2026-10-19
范围：仅针对 B 线（多 Session KV 生命周期管理），不涉及 Slack 回收 / 热感知配置选择。
依据：`code/multisession_kv/` 下的实现、`results/` 下的真机与离线分析产物，以及
`docs/mobile_llm_kv_problem_formulation_and_method.md`、`docs/weeks/1012.md`。

---

## 0. 结论摘要

项目已经完成两件有分量的事：

1. **问题存在性得到真机验证**：容量受限的 LRU 在 4/8 Session 交错访问下出现真实驱逐、
   重复 Prefill 与 TTFT 上升；
2. **方法与 Oracle 上界之间有明确空间**：中间容量点上未来感知策略相对 LRU 还有
   16.9%–49.9% 的额外 Prefill 减少空间。

但现有证据还不足以支撑"提出了一个有效的在线策略"这一陈述。核心问题有三个：

- **收益归因不清**：实测降幅中 59%–100% 来自"会话结束即释放"这一几乎不需要算法的信号，
  价值函数只贡献 0%–41%（取决于容量点）；
- **评测负载对 LRU 过于敌对**：round-robin + 等长 Session + 全部跑到最后，恰好是
  价值函数最没有信息量的场景；
- **最强的发现被放在了条件实验里**：同一策略在 `queued_next_turn` 下能恢复
  94%–98% 的 Oracle gap，而 `serial_arrival` 只有 41%–61%。差距全部来自"调度器
  是否暴露就绪队列"，说明**系统接口比驱逐算法本身更重要**。

建议把论文主线从"一个新驱逐策略"重构为"收益从哪来、边界在哪、需要什么接口"。
所有支撑这一重构所需的新实验都可以离线完成，不占用手机。

## 2. 收益归因：把 30% 拆开看

这一节的数字直接由 `lifecycle_summary.csv` 的 `serial_arrival` 行做算术拆解得到，
不涉及重新跑实验，但能立刻改变对结果的解读方式。

定义：

```
Close 贡献   = (CloseAware-LRU − LRU) / (Lifecycle-LRU − LRU)
价值函数贡献 = (Lifecycle-LRU − CloseAware-LRU) / (Lifecycle-LRU − LRU)
```

| 点 | LRU | +Close | +价值分数 | 增量合计 | Close 贡献 | 价值函数贡献 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| N4/C2 | 2.3% | 10.9% | 13.5% | +11.2 | 76.8% | 23.2% |
| N4/C3 | 6.1% | 21.9% | 32.7% | +26.6 | 59.4% | 40.6% |
| N8/C2 | 2.3% | 6.7% | 6.7% | +4.4 | 100.0% | 0.0% |
| N8/C4 | 16.3% | 27.1% | 29.8% | +13.5 | 80.0% | 20.0% |
| N8/C6 | 16.3% | 34.4% | 41.8% | +25.5 | 71.0% | 29.0% |

### 2.1 解读

**（a）主要收益来自生命周期信号，不是打分函数。**
五个点里 CloseAware-LRU 一个规则（"会话显式结束就释放"）就拿到了 59%–100% 的收益。
在 N8/C2 上，加入价值函数后复用率**一个字都没变**（6.7% → 6.7%），说明该容量点下
打分函数的所有决策都与 LRU 次序一致。

**（b）Oracle 的信息量几乎全在"下一次访问何时到来"。**
Belady 与 token-optimal 在所有点上几乎重合（28.3 vs 29.5、50.4 vs 51.8、42.9 vs 44.0、
57.1 vs 58.0，差距 ≤1.4 个百分点）。这意味着**按缓存 token 数加权价值几乎没有额外收益**，
全部可用信息是未来访问距离。当前价值函数里的 `cached_tokens` 项因此是一个
"看起来合理但实证无贡献"的组件。

**（c）剩余空间要靠预测，不是靠调参。**
`serial_arrival` 下方法恢复了 41%–61% 的 Oracle gap，剩余 39%–59% 需要真正的
在线下一次访问预测才能兑现。这部分空间是真实存在的，但它属于"预测问题"，
不属于"打分函数调参问题"。

### 2.2 对论文的影响

如果按"Lifecycle-LRU 比 LRU 好 30%"来写，审稿人会立刻问：把 close 信号给 LRU
是不是也有 30%？答案是"是，而且只有 30%"——那方法本身的增量就只有 0–10.8 个
百分点。必须以**归因拆解**的形式主动呈现，并把结论落到"生命周期接口的系统价值"上。

## 3. 代码实现与设计文档的差距

`mobile_llm_kv_problem_formulation_and_method.md` §4.2 定义的打分是：

```
S_i = w_r·I(READY) + w_w·e^(−Δt/τ)·I(WAITING/BLOCKED) + w_k·K̃_i
```

而 `lifecycle_policy.py:44-67` 的实际实现是：

```python
interval_scale = ema if ema is not None else session_count
recency = exp(-idle / max(interval_scale, 1.0))
cached_value = cached_tokens / max_cached
scores[resident] = recency + cached_value
```

差异与影响：

1. **三个权重全部硬编码为 1**。文档承诺"权重先用离线消融确定，再固定用于手机实验"，
   但目前没有任何权重消融。`w_r` 在 `serial_arrival` 协议下不生效，因为该协议下
   只有正在派发的请求是 READY，其余驻留 Session 一律为 WAITING。
2. **`idle` 是请求序号差，不是墙钟时间**；`ema_interval` 的初始 fallback 是
   `session_count`。在 round-robin 负载下，所有 Session 的 EMA 都收敛到 ≈N，
   `recency` 项趋近常数，打分实质退化为"LRU + 缓存大小 tie-break"。
3. **`cached_tokens` 取 `input_tokens[index]`**（`analyze_lifecycle.py:192`），
   不含本轮生成的 token（配置为 64），低估约 10% 的 KV 价值。

### 3.1 为什么这不是 bug，但仍然是问题

这些简化让实现保持可解释，本身无可指摘。真正的问题是：**当前评测负载恰好让
价值函数最没有信息量**。round-robin 下访问间隔几乎是常数，`exp(-idle/EMA)`
无法区分任何 Session。

真实场景中 think-time 是重尾的、会话长度是重尾的、会话流行度是不均的。在这些
负载下 EMA 才有区分能力。因此：

- 当前结果**不能证明**价值函数有用；
- 当前结果也**不能证明**价值函数没用。

这一点必须写进局限性，并且用 §6 的负载敏感性实验来回答。

## 4. DONE 信号的真实风险

文档已正确使用 `controlled_protocol` 标注，这一点是规范的。但模拟器里
`final_request` 直接取每个 Session 在 trace 中的最后一次出现
（`analyze_lifecycle.py:99`），隐含两个乐观假设：

1. **零延迟**：最后一轮请求结束后，close 立即到达；
2. **全覆盖**：每个 Session 都必然产生 close。

真实应用中更接近的情况是：

- 用户切走 app 触发的是 `onStop`，会话可能长期甚至永久不关闭；
- 会话关闭可能滞后数十秒；
- 后台被系统回收时根本没有 close 事件。

因此当前 59%–100% 的"close 贡献"是**上限值**，不是期望值。

**这是唯一一个必须补、且完全不需要手机的实验**：把 close 建模为
`coverage ∈ {100%, 75%, 50%, 25%}` × `delay ∈ {0, 1, 5, 20}` 个请求，
在现有模拟器上重跑。如果 coverage 降到 50% 时收益从 30% 掉到 8%，那论文的
标题就该是"生命周期接口值多少"，而不是"新驱逐策略"。

## 5. 指标层面的两个隐患

### 5.1 Prefill 时间降幅与 TTFT 降幅不自洽

| 点 | Prefill 时间降幅 | TTFT 降幅 | 比值 |
| --- | ---: | ---: | ---: |
| N4/C2 | 11.0% | 1.4% | 0.13 |
| N4/C3 | 25.2% | 12.6% | 0.50 |
| N8/C2 | 5.2% | 1.8% | 0.35 |
| N8/C4 | 11.6% | 11.1% | 0.96 |
| N8/C6 | 25.4% | 20.6% | 0.81 |

同一模型、同一 TTFT 定义下，这个比值不应在 0.13–0.96 之间大幅跳动。
可能原因：

- prefill-time 只在"确实发生 prefill 的请求"上聚合，而 TTFT 包含全部请求；
- 两条曲线的分母不同（每请求均值 vs 总量）；
- TTFT 中混入了缓存管理、队列等待等与 prefill 无关的分量。

**投稿前必须澄清**，否则属于会被直接质疑的数据一致性问题。

### 5.2 BFCL N8/C6 的 RSS 差是采样伪影

BFCL Base N8/C6 报告 RSS 差 −34.02 MiB，Long-Context 同点 −67.79 MiB。单个
Session 的 KV 约 36 MiB，这个差值相当于"少了两个 Session"——但策略方向是
**保留更多**，不是更少。只能是单点 PSS 采样恰好落在不同驱逐状态上。

建议改为：

- 报告 RSS 时间序列或驻留槽位归一化后的值；
- 或直接报告"按驻留槽位数归一化后的每槽 RSS"，并注明采样方法。

否则会引出"你到底是省了内存还是多了内存"的质疑，这个问题本可以不出现。

### 5.3 温度混杂

`hammer_matrix_lifecycle_phone_t30.yaml` 中 `repeats: 1`，配对成员运行时间不同，
起始温度可在 27°C–29.9°C 之间变化（门槛为 30.0°C）。N4/C2 的 1.4% TTFT 变化
很可能就淹没在这个波动里。

建议在分析中把 `temperature_start` 作为协变量做回归，或至少并列报告两种策略的
起始温度分布，证明配对是平衡的。

## 6. 被低估的最大发现：接口 > 算法

现有结果里最有价值的一组对比被放在了"条件实验"位置：

| 协议 | Oracle gap 恢复 | 说明 |
| --- | ---: | --- |
| `serial_arrival` | 41.3% – 61.2% | 保守主结果 |
| `queued_next_turn` | 94.3% – 97.8% | 被标为条件实验 |

两种协议使用**同一个策略、同一套代码**，唯一差别是"调度器是否把就绪队列暴露给
KV 管理层"。这个差别让 Oracle gap 恢复从 41% 跳到 95%，翻了一倍多。

而这个假设并不离谱：应用内的 LLM 服务天然知道自己排队的下一轮请求。

### 6.1 建议的表述方式

不要把它写成"我们还做了一个条件实验"，而应写成：

> 在手机多会话场景中，KV 驱逐策略的可达收益上限主要由**调度器与缓存层之间的
> 接口**决定，而非驱逐算法本身。当上层能够暴露就绪队列时，一个简单的
> 就绪感知策略即可恢复 95% 以上的 Oracle 空间；当只能观测串行到达时，同样的
> 策略只能恢复 41%–61%。

这样贡献从"又一个 LRU 变种"变成"一个接口设计论证"。这是本次分析中我认为最
值得采纳的一条重构建议。

### 6.2 需要补的证据

- 在手机端真实实现一次 `queued_next_turn`（哪怕是受控协议注入），验证离线
  数字在真机上成立；
- 明确区分"就绪队列可见"与"精确 LCP 可见"两种粒度，分别测量各自贡献
  （目前二者是捆绑的）。

## 7. 缺失实验，按性价比排序

| 优先级 | 实验 | 设备时间 | 产出 |
| --- | --- | --- | --- |
| 1 | 负载模型敏感性（Zipf 流行度 / Pareto 会话长度 / think time） | 0 | 方法的适用边界相图 |
| 2 | Close 覆盖率与延迟扫描 | 0 | 生命周期接口的价值曲线 |
| 3 | 容量补点 N8/C7、N16 | 少量 | 验证 C=N−1 的单受害者区 |
| 4 | 温度混杂检查（用现有数据回归） | 0 | 修正 N4/C2 等弱结果 |
| 5 | BFCL Base 补完；Long-Context 砍到每点 6 组 | 中 | 跨数据集泛化 |
| 6 | 真实 Android close 信号最小 demo | 少量 | 可信度提升 |

### 7.1 负载模型敏感性（优先级最高）

用现有 AllKeep trace 重采样生成：

- 会话流行度 Zipf(α)，α ∈ {0.6, 1.0, 1.4}；
- 会话长度 Pareto 分布；
- 请求到达服从泊松 + think time 分布。

然后在同一个离线模拟器上跑 LRU / CloseAware-LRU / Lifecycle-LRU / Oracle，
画出"收益 vs 负载偏斜度"的相图。这一步将直接回答：

- 在真实偏斜负载下，LRU 是不是真的这么差？
- 方法的收益区间在哪里，什么时候失效？

**如果 Zipf 下 LRU 表现大幅改善、收益掉到个位数，这本身是一个重要的负结果**，
而且能让论文的可信度显著提升。

### 7.2 容量补点

现有高收益点集中在"仅剩一个可淘汰对象"的区域：N4/C3（N−1）、N8/C6（N−2）。
N8/C7（N−1）大概率收益更高，但目前缺失。补 N8/C7 和 N16/C8 可以刻画收益随
`slots / sessions` 的变化曲线，是很好的论文主图。

## 8. 不建议做的事

1. **不要训练下一次访问预测器。** Belady 是上限，当前已恢复 41%–61%，剩余空间
   对应约 10–15 个百分点的复用率；因果预测器即使拿到一半，投入产出比也远不如图 1
   的敏感性曲线。
2. **不要扩大 LRU 全量矩阵。** 现有 Stage-3 缩减矩阵已经足够支撑问题存在性论证。
3. **不要正面与 Libra 竞争"换出"。** 那是它的主场（chunk 级压缩 + swap + 重算
   流水线）。正确做法是实测 `evict → restore` 成本，论证在 QNN 静态图 +
   128-token block padding 条件下，固定槽位是合理的设计选择，把限制转化为
   有依据的设计依据。
4. **不要把受控协议的 close 结果表述为自然 Agent workload 的收益比例。**

## 9. 写作定位与论文骨架

建议主线：

> 手机端多会话 KV 驻留的收益从哪来、边界在哪、需要什么系统接口才能兑现。

四段式结构：

1. **问题与负对照**：容量不足导致真实驱逐与重复 Prefill。保留 N2/C1 这个
   "无策略空间"的负对照——它证明作者没有把不可避免的容量限制包装成方法收益。
2. **收益归因**：close 信号贡献 59%–100%，价值函数贡献 0%–41%；Belady ≈
   token-optimal，说明信息全在访问距离而非 token 价值。
3. **接口价值**：`queued_next_turn` 下恢复 95%+ 的 Oracle gap，与
   `serial_arrival` 的 41%–61% 形成鲜明对比。
4. **失效边界**：负载偏斜（§7.1）、close 覆盖率（§7.2）、容量拐点。

这条叙事线的优点是：每一段都已有数据或只需离线实验，且不依赖"我们比 LRU
好 30%"这种容易被推翻的陈述。适合 MobiSys / SenSys / EuroSys 的系统论文定位。

---

## 10. 如果只能做两件事

1. **§7.1 负载模型敏感性分析**——决定方法是否成立的关键实验，离线可完成。
2. **§7.2 Close 覆盖率与延迟扫描**——量化当前 30% 收益中有多少是接口红利。

这两张离线曲线可以把方法论从"一个策略"升级为"一张地图"。
