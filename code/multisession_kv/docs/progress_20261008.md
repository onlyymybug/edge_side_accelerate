# Multi-session KV experiment progress — 2026-10-08

## Scope decision

The research target is now explicitly limited to session-level KV retention for
interleaved requests on one resident on-device LLM. HammerBench and BFCL are
workload sources, not evidence of end-to-end agent execution. The current replay
does not evaluate planning, tool correctness, multi-agent cooperation, or task
success. The first deployable method will be Lifecycle-LRU using only causal
READY/WAITING/BLOCKED/DONE signals; learned next-use prediction and token-level
eviction are out of scope for the first version.

## Implemented pipeline

The experiment code is under `/home/lyyyy/edge_side_work/code/multisession_kv`.
It is separate from the phone runner bundle and currently provides:

- `prepare_data.py`: immutable local dataset provenance and schema inventory;
- `build_trace.py`: HammerBench cumulative-snapshot parsing, filtering,
  stratified Session sampling, prompt serialization and tokenization;
- `backend_adapter.py`: resident QNN JSONL runner adapter;
- `replay.py`: Grouped/RoundRobin plus NoReuse, AllKeep, SingleSlot and
  host-directed LRU replay;
- `collect_android.py`: one-second Android RSS/VmHWM/thermal sampling;
- `validate_results.py`: trace and runtime invariant checks;
- `analyze.py`: CSV/JSON run aggregation;
- `run_matrix.py`: seeded randomized, immutable and resumable matrix execution;
- `calibrate_temperature.py`: idle thermal baseline collection;
- `analyze_matrix.py`: passed-job matrix aggregation and completion checks;
- `tests/test_core.py`: parser, LCP, fixed-tool and scheduling regression tests.

The existing `pace` conda environment is required because system Python does
not include `tokenizers`. No new package was installed.

## Redmi replay smoke

All runs used the resident QNN runner, one PID and one model load. Initial
16-token diagnostic runs intentionally ignored EOS; they only validated the
mechanism and must not be combined with formal natural-trace measurements.

For the same first two Sessions under AllKeep RoundRobin:

| Variant | Input | Prefill | Reused | Median TTFT |
| --- | ---: | ---: | ---: | ---: |
| `fixed_tools` | 2,111 | 1,090 | 1,021 | 319.28 ms |
| `native_tools` | 1,600 | 1,556 | 44 | 425.43 ms |

The two second-turn runtime LCP values were 497/524 for fixed tools and 20/24
for native tools. Thus candidate-tool changes destroy most of the reusable
prefix in these samples even though native prompts are shorter.

On the fixed-tools trace, NoReuse and SingleSlot each Prefilled all 2,111
tokens. Their median TTFT was about 593/592 ms, versus 319 ms for AllKeep.

A later formal-format smoke used a 64-token maximum, `stop_on_eos=true`, one
warm-up excluded from results, telemetry, and complete hashes. Six requests
generated 19–26 tokens before EOS. Offline and runtime LCP matched exactly:

- input tokens: 3,155;
- Prefill tokens: 1,104;
- reused tokens: 2,051 (65.0%);
- median TTFT: 143.40 ms;
- peak RSS: 89,784 KiB;
- skin temperature: 29.38 to 30.43 C.

These are smoke results from different small Session subsets, not repeated
formal estimates.

## Formal work status and narrowed next step

The randomized/resumable launcher and recovery gate are implemented. It rejects
configuration/trace/runner hash changes within an existing result root, preserves
failed attempts, rejects externally powered runs, and merges nominal LRU ratios
that map to the same physical slot count.

Two 60-second Redmi idle measurements were collected after the matrix smoke. The
first retained a cooling transient (28.431 to 27.288 C). The second was stable:
12 skin samples, median 27.139 C and range 27.085--27.224 C. The formal start gate
is therefore explicitly set to 28.2 C for three consecutive samples 10 seconds
apart. This threshold is device- and environment-specific.

The paired pilot and the reduced 50-Session Stage-3 population matrix are
complete. The next required work is not another broad LRU matrix. It is:

1. implement offline causal ablations for CloseAware-, ReadyAware- and
   Lifecycle-LRU;
2. distinguish explicit runtime lifecycle events from future-derived what-if
   labels;
3. deploy the smallest effective policy at N4/C2, N4/C3, N8/C2, N8/C4 and
   N8/C6;
4. use BFCL V4 reference-history traces only as a generalization workload after
   the HammerBench method result is established.

The first offline causal ablation is now implemented in `analyze_lifecycle.py`.
It validates all 42 selected group/capacity cases against measured phone LRU and
separates `serial_arrival` from the stronger `queued_next_turn` visibility
assumption. Under conservative serial arrival, Lifecycle-LRU reduces remaining
Prefill versus LRU by 11.5% at N4/C2, 28.4% at N4/C3, 4.4% at N8/C2, 16.1% at
N8/C4 and 30.5% at N8/C6. Thus the offline gate passes at both N=4 and N=8;
N8/C2 remains a negative control for phone validation. These values are token
replay estimates, not measured TTFT improvements.

The conservative serial-arrival policy is now integrated into `replay.py`. A
first real N8/C4 phone smoke completed 36 requests with 6,203 reused and 15,151
Prefill tokens, exactly matching the offline policy replay for the same group.
It emitted 36 READY, 36 RUNNING, 28 WAITING and 8 DONE events, all labeled
`controlled_protocol`; 19 capacity evictions occurred. Host policy computation
was 0.913 ms total (0.111 ms maximum per request). The phone run started at
27.32 C and peaked at 32.38 C. A separate 30.0 C matrix configuration now
contains 84 matched LRU/Lifecycle-LRU jobs; the 28.2 C run remains smoke only.

An independent paired pilot matrix was added before committing to the full
2,658-job HammerBench matrix. It uses the first fixed group for each of 2/4/8
Sessions and crosses the two schedules with NoReuse, AllKeep, SingleSlot and
the distinct realizable LRU slot budgets, with three repetitions. This produces
102 randomized jobs while preserving matched inputs within each Session count.

The paired Pilot subsequently completed all 102 jobs without failure or retry.
All 34 configuration groups contain three repetitions. Median run-level CV is
0.60% for useful Prefill throughput, 0.27% for Decode throughput, 0.62% for
median TTFT and 0.27% for trace makespan. The mechanism-validation report and
figures are under `results/hammer_matrix_pilot/analysis`.

Pilot evidence was used to define `hammer_matrix_stage3_reduced.yaml`. It omits
Grouped LRU/SingleSlot combinations shown to be equivalent, omits duplicate
RoundRobin NoReuse where SingleSlot is the realized zero-reuse baseline, and
uses one run per fixed population group. All 50 Sessions remain covered by
fixed 1/2/4/8 group partitions. The resulting matrix has 388 jobs rather than
2,658 (100 single-Session controls, 90 Grouped controls and 198 RoundRobin
capacity-pressure runs).

The reduced Stage-3 matrix completed all 388 jobs without failure or retry.
Primary population estimates exclude the final two-Session tail group from the
nominal 4- and 8-Session partitions while retaining those runs in the manifest.
Paired group-level bootstrap analysis, CSV/JSON tables, figures and the final
report are under `results/hammer_matrix_stage3_reduced/analysis`.

An offline whole-Session cache simulator was then calibrated against all 104
full-group LRU/budget cases; simulated and measured reused-token totals match
exactly. Belady farthest-next and a token-optimal dynamic program reveal no
policy opportunity at one slot, but reduce remaining Prefill relative to LRU by
16.9--49.9% at the intermediate 4/8-Session budgets. The Oracle is explicitly
reported as a non-causal upper bound. Results are under
`results/hammer_matrix_stage3_reduced/oracle_analysis`.

The 30.0 C Lifecycle-LRU phone validation matrix is now complete: all 84 jobs
passed and all 42 LRU/Lifecycle-LRU pairs are available. One job required a
second attempt after a runner-initialization timeout; there were no request-time
policy failures. Every run loaded the model exactly once, and all 84 measured
reused-token totals match the conservative offline `serial_arrival` simulation.

At N4/C2, N4/C3, N8/C2, N8/C4 and N8/C6, Lifecycle-LRU reduced Prefill tokens
by 11.5%, 28.4%, 4.4%, 16.1% and 30.5%, respectively. Paired group-bootstrap
TTFT intervals exclude zero at N4/C3, N8/C4 and N8/C6; makespan intervals
exclude zero at N4/C3 and N8/C6. Mean paired peak-RSS differences stay within
0.23 MiB, total Lifecycle policy computation was 18.639 ms, and the maximum
single-request decision time was 0.278 ms. The final reproducible analysis is
under `results/hammer_matrix_lifecycle_phone_t30/analysis` and is generated by
`analyze_lifecycle_phone.py`.
